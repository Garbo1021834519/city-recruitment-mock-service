## 需要优先处理的问题

P1 表示应在真实业务试运行前修复；P2 表示功能补齐或状态准确性问题。

### R1 · P1：导出绕过城市数据权限

位置：`src/modules/files/file.routes.ts:41-42`。导出直接执行全表 SQL，没有复用列表的数据范围过滤。

**已复现：**使用仅有城市 1 范围的 `local-recruiter` 登录，新增城市 99 的工厂标记 `AUDIT_HIDDEN_FACTORY`。普通工厂列表不包含该记录；调用工厂 Excel 导出接口却返回 HTTP 200，工作簿包含该标记。

**影响：**列表权限无法阻止跨城市批量读取。岗位、假期等导出也应逐个核对，不能仅修复工厂这一条路径。本轮已动态确认的是工厂导出。

**处理与验收：**让导出与对应列表共享权限查询；无范围用户不能导出全量数据。为不同城市用户分别比对列表与导出中的记录集合。

### R2 · P1：清空一个设备的未读数，会影响其他设备

位置：`src/modules/agent/agent.routes.ts:127`。

```sql
WHERE device_code=(SELECT device_code FROM agent_devices WHERE id=?)
```

`agent_devices` 没有独立的 `device_code` 列，该字段存储在 `data_json` 中。在此 SQL 中，SQLite 将子查询里的列名解析为外层会话的列，导致条件对多个设备的会话成立。

**已复现：**招聘员对有权限的设备 1 调用清未读接口，HTTP 200；另一个未分配设备的未读数从 **7 变为 0**。

**处理与验收：**使用完成鉴权后已解析的 `deviceData.device_code` 作为更新参数。准备两个设备各自的会话，清空 A 后 B 的未读数和更新时间都不变。

### R3 · P1：删除工作流会清空设备身份和连接配置

位置：`src/modules/agent/agent.routes.ts:147`。

接口把整个 `data_json` 更新为 `{}`，同时删除 `device_code`、`recruiter_id`，以及存放在同一对象里的 Dify 配置。

**已复现：**删除设备 1 的工作流后，原本含有设备和招聘员标识的对象变为 `{}`。随后同设备的新签名消息返回 **HTTP 502**：`Enabled message device not found`。

**处理与验收：**仅移除工作流相关字段；保留身份、归属及连接配置。删除前后均应能接收入站消息；其他配置值逐项保持一致。当前复现基于默认设备，即使没有已上传工作流也能触发破坏。

### R4 · P1：AI 生成期间人工接管，仍继续发出回复

位置：`src/modules/messaging/message-automation.ts:59-62,102-121`。接管状态只在调用 Dify 前读取一次，异步等待结束后直接调用发送通道。

**已复现：**暂停 Dify 返回 → 将会话 `takeover` 改为 1 → 恢复生成。结果仍调用模拟发送并产生 `simulated` 出站消息。

**处理与验收：**在发送前重新检查接管状态，并用会话版本或取消机制约束生成、发送与接管的先后关系。还需修复 `agent.routes.ts:30` 查询消息时固定返回 `takeover:false` 的问题，让前端读取真实状态。

**验收场景：**生成前接管、生成中接管、待发队列中接管，都不能产生后续自动回复；解除接管后的处理策略应明确。

### R5 · P1：发送中断后重放事件，消息卡在 sending

位置：`src/modules/messaging/message-automation.ts:99`、`src/modules/messaging/message-events.ts:43-45`。

`markDeliverySending` 仅允许 `queued/failed` 进入发送。若进程在标记 `sending` 后退出，持久化状态没有租约、超时回收或恢复路径。

**已复现：**构造进程中断会留下的 `sending` 投递记录，重放相同签名回调，返回 **HTTP 500**：`Delivery is not available for sending`；记录仍为 `sending`，尝试次数仍为 1。相同事件在处理中被并发重投，也会遇到这一限制。

**处理与验收：**增加投递租约和恢复处理；重复处理中事件返回可识别的处理中状态。恢复时必须结合通道幂等键或发送结果查询，避免盲目重发造成重复触达。验证生成中退出、发送请求中退出、发送成功后落库前退出三个时点。

### R6 · P1：同一会话并发消息会拆分 AI 上下文、倒序发送

位置：`src/modules/messaging/message-automation.ts:59,102-117,133-134`。没有按会话排队，同一会话的多个请求可同时读取旧的 `external_conversation_id`。

**已复现：**第一、第二条消息同时处理，两次 Dify 调用都不带会话 ID。让第二条先完成、第一条后完成，最后保存的上下文变为第一条的 `context-first`，会话摘要也回退为第一条回复。

**处理与验收：**按业务会话身份串行处理，或采用明确的消息合并策略；多实例部署时也应生效。同会话连续消息应共享正确上下文和发送顺序，不同会话可并行。

### R7 · P1：人工回复、激活仍然虚报“已发送”

位置：`src/modules/agent/agent.routes.ts:32`、`src/modules/activation/activation.routes.ts:108-114`、`src/modules/activation/activation.jobs.ts:82-110`。

**已复现：**

### 修复之间的依赖和发布注意点

- **R1、R2、R3 可以优先局部修复。**共享权限查询仍应分别回归调用方；R2、R3 的历史损坏需要单独的数据修复方案，修好代码不等于修好了旧数据。
- **R4、R5、R6、R7、R9 应先统一设计，再分步提交。**它们共同修改消息的认领、顺序、取消与结果记录。避免不同修复分别引入互不兼容的状态或两套重试机制；会话排队和发送恢复也要覆盖激活、人工回复等入口。
- **引入 worker 会改变运行行为。**过去堆积的任务可能开始执行。发布前需盘点旧任务、发送资格及目标用户，明确哪些继续、取消或人工确认；不要在没有处理规则时直接放开历史积压。
- **数据库新增字段优先采用可兼容的增量迁移。**回调状态、前端展示和消费端应同步约定；若回退应用，保留投递与通道结果记录，避免回退后重复发送。具体迁移及回退脚本应在实现确定后编写和验证。
- **影响范围仍需随实现更新。**以上是当前源码支持的预估。修复 PR 应补充实际修改文件、接口变化、迁移、执行过的回归结果及未验证项目；发现新增调用方或新的通道约束时，应扩大评估并更新报告。

## 企微与真实业务数据的实际进度

`src/modules/messaging/message-channel-provider.ts` 只有 `MockMessageChannelProvider`；配置为其他通道会抛出 `Unsupported message channel provider`。因此这版模拟闭环不能作为“已接通招聘员企微私聊”的证据。

上一份《企业微信API接入断点分析与实施方案》仍可作为接入设计参考，但其中关于 JWT 阻断回调、HTTP Dify 未接线等旧判断应以上面的修复表为准。下一步应完成已选私聊链路的真实身份映射、官方接入方式、接收进度保存、去重与恢复，再做真实账号端到端验收。

`src/db/seed.ts` 明确注明现有城市关联、工厂、岗位、候选人及电话为演示数据；其中还会在启动时补充演示账户和业务记录。原始“填真实业务数据”的目标尚未完成。需要业务方提供获准使用且可核实的岗位、薪资、招聘状态和联系方式，再通过校验后的导入流程入库。正式环境应能够关闭演示数据初始化，并校验必要配置，避免默认演示值混入真实业务。

## 建议交给开发 Agent 的执行顺序

1. 先处理 R1、R2、R3：堵住导出越权、跨设备更新与配置误删。
2. 处理 R4、R5、R6：完善会话串行、接管取消、投递租约与幂等恢复。
3. 处理 R7、R9：统一人工、自动回复和激活状态，打通任务消费，消除假成功。
4. 处理 R8、R10：补齐数据导入上传和干净环境启动验证。
5. 按已确认的企微好友私聊方案完成真实接入，用授权测试账号验证接收、生成、人工处理、发送确认及断线恢复；之后再引入真实业务资料。

每项修复应提交对应的边界回归测试和结果证据，不能仅以现有 100 项正常流程测试通过作为完成标准。
